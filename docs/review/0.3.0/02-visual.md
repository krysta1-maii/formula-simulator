## 1. 审阅范围与方法

静态审阅覆盖 `src/js/10-scene.js`（相机、灯光、材质、路面、标注）、`src/js/20-car.js`（程序化车身、贴花、资源释放）、`src/js/22-car-dynamics.js`（车轮、悬架、防倾杆、更新循环），以及 `src/index.template.html` 与 `src/styles.css` 中与画布、面板、底部工具栏、标注相关的结构；同时核对了 README 的视觉声明、DESIGN 第 4 节与第 20.6 节、acceptance 的 UI 覆盖声明，以及 0.2.0 两轮审阅的视觉相关发现（低高度横屏裁切、轮载箭头标尺、材质释放等），避免把已修复项当作新问题。

1. 用 `tools/browser-runner.mjs` 启动无头 Chrome；每次启动使用随机调试端口与临时 `user-data-dir`，结束即关闭，未占用 8731 端口，也未留下 Chrome 进程。

### 2.4 几何重建后的对象与资源一致性

连续 5 次轴距重建（3.62 → 3.76 → 3.90 → 3.70 → 3.55 m）实测：

- 每次重建后车辆网格数恒为 574，`carRoot` 子节点 2（bodyPivot + dynamicGroup），`dynamicGroup` 子节点 90，`bodyPivot` 子节点 2（bodywork + internalSuspension）；
- `wheel-FL/FR/RL/RR`、`bodywork`、`dynamicSuspension`、`internalSuspension` 每个名字均恰好 1 个，无旧对象残留；
- `renderer.info.memory` 稳定为 411 个几何、16 张纹理；每次重建 `lastBuild` 均为 `instanceMaterialCreated=7, instanceMaterialDisposed=7, geometryDisposed=387`；
- 四轮位置随轴距正确变化（前轮 x 由 ±1.775 变为 ±1.950 等），场景几何版本与物理版本一致（`geometryMismatch=false`）。

这支持“反复改尺寸不产生旧对象残留、材质/几何释放计数稳定”的判断；像素级前后一致性未做，因为两次截图处于不同仿真时刻。

### 2.5 未复现的渲染问题

在本次三种视口、五个预设、四个剖视与三种动态姿态的截图里，未观察到 z-fighting、阴影贴图瑕疵、透明排序导致的明显闪烁、文字方向错误或车体比例异常。地面接地点环、轮载箭头、CG 投影与车身姿态同步；8°/7° 倾斜时箭头随接地点移动，箭头高度与载荷比一致（实测箭头高度 0.14–0.34 m，对应 918–2241 N）。

### P3-3（观察，非缺陷结论）：每帧 521 次 draw call、574 个网格，几何未合并

### 3.1 视觉改进建议（非缺陷）

- xray 车身使用 `MeshBasicMaterial opacity 0.07, depthWrite:false, DoubleSide`（`10-scene.js:601-608`），在剖视近景中会产生大量半透明重叠面，视觉上像“烟状碎片”；机构本身可见且能辨认，属于 DESIGN 已声明的剖视表现，不是错误。若后续提升品质，可用轮廓线/描边加低透明度填充替代多层透明面。
- 载荷箭头统一使用青色材质（`MAT.loadArrow`），没有按载荷大小改变颜色；代码里计算的 `hueScale` 只用于接触环透明度和引线（`10-scene.js:1071-1085`）。这不违反“长度正比于载荷”的说明，但可作为可读性改进：低载/高载用色阶或标签强调。
- 地面阴影是固定比例的椭圆贴图（5.8 m × 2.35 m，`10-scene.js:931-939`），只跟随车体 x/z 与横摆，不随俯仰/侧倾缩放；在 8°/7° 倾斜下仍贴合地面，视觉可接受，但大姿态时阴影与车轮接地点不再严格对应。属已声明简化，不建议当缺陷处理。

## 4. 测试与文档缺口

1. **竖屏取景没有自动断言。** `tools/test-ui-browser.mjs:167` 的视口矩阵是 844×390、667×375、1024×400、1280×720，不含 390×844，也没有“车辆投影包围盒在视口/安全区内”的断言；`tools/test-camera.mjs` 的 19 项只校验预设角度、投影和交互，不校验任意视口下的取景完整性。因此 README:259 的“完整看到赛车”无法被现有测试发现为不成立。
2. **面板遮挡没有测试。** `test-ui-browser` 校验面板自身在视口内，但不校验面板与车辆/标签/箭头是否相交；1280×900 默认取景与四个轴向预设的遮挡因此漏检。建议新增“车体屏幕包围盒与展开面板矩形不相交（或安全区适配后相交面积为 0）”的断言。
3. **导出图内容只有目视验证。** 没有断言导出 PNG 的尺寸、叠加文本与版本号；`DESIGN.md v0.2` 残留即由此漏过。可在浏览器中拦截 `HTMLAnchorElement.click`/`toDataURL`，或解码导出 PNG 做像素/文本检查。
4. **动态/标注回归只覆盖默认水平姿态。** 现有浏览器测试覆盖脉冲、暂停、滑移，但没有把“8°/7° 倾斜 + 剖视 + 标签”组合起来检查标签是否被面板遮挡、箭头是否落在地面、剖视部件是否在相机近平面内。
5. **没有视觉回归基线。** 本项目没有截图快照对比，透明排序、z-fighting、材质/贴花偏移这类问题只能靠人工；本次未发现此类问题，但后续阶段三/四加入更多网格后风险会上升。
6. **未覆盖双击重置、右键/中键/Shift 平移。** 源码实现了这些路径（`10-scene.js:1363-1490`），但 `test-camera` 只覆盖左键拖动、滚轮和正交按钮；本轮尝试用 CDP 直接验证右键/中键/双击时，无头 Chrome 启动在负载下超时，未取得结果（见覆盖限制）。

## 5. 覆盖限制

- 渲染后端是无头 Chrome 的 SwiftShader，不是 GPU 实机；本报告不对帧率、抗锯齿质量、真实设备上的阴影/透明排序做结论。截图中的暗部噪点和边缘锯齿部分来自软件渲染。
- 只覆盖 1280×900、390×844、844×390 三种视口；未覆盖 667×375、1024×400、1280×720、1920×1080、DPR=2 以及 360/430 px 等边界宽度。
- 动态姿态只测了 8°/7° 静平衡、0.18 s 俯仰脉冲与 0.22 s 侧倾脉冲；未覆盖 ±10°/±25 mm 极限行程、低刚度/低阻尼组合、转向 ±15° 下的杆件穿插，也未覆盖车轮离地（该模型已在 README 声明不建模）。
- 剖视与杆件穿插判断主要依据截图与端点/杆长数值；没有做逐三角形—三角形相交检测，因此“未观察到穿插”不等于“数学上无穿插”。
- 几何重建用对象/材质/几何计数与轮位验证一致性，没有做重建前后像素 diff（两次截图处于不同仿真时刻，不能直接比较）。
- 右键/中键/Shift 平移与双击重置未取得独立的 CDP 实测结果，只做了源码核对与既有相机测试（左键拖动/滚轮/正交）的复跑；这构成本轮相机交互覆盖的缺口。
- 面板遮挡是否属于“DESIGN 已声明简化”：DESIGN 未声明“面板会覆盖 3D 场景且取景不避让”，因此按实现/构图缺陷处理；若产品明确接受“面板覆盖为设计选择”，则应把 README 的“完整看到赛车”改为“关闭面板后完整看到赛车”，并将 P2-1/P2-2 降级为文档一致性问题。

## 6. 待验证假设（不计入确定发现）

**鼻锥号码贴花可能悬浮于曲面之上。** `src/js/20-car.js:1247-1251` 将“01”贴花放在 `[xF + 0.21, 0.430, 0]` 的水平面上，旋转为 `[-π/2, 0, -0.22]`；该旋转仍保持平面法线为 +Y（局部 X 只绕世界 Y 旋转），而 `monoSections`（`20-car.js:753-768`）在 `x=xF+0.21` 附近的顶面高度约为 0.406 m，贴花后缘（x≈xF+0.36）处顶面约 0.369 m。按静态几何估算，贴花后缘可能高出鼻锥约 20–60 mm。由于截图距离远、贴花很淡，本轮没有取得能确认悬浮的近距离证据，故仅列为待验证假设，不作为缺陷。验证方法：在 0.43 m 高度向 -Y 方向对鼻锥顶面做射线求交，比较贴花平面与曲面距离；或近距离侧视截图。

## 7. 结论

0.3.0 的渲染管线、悬架视觉同步、资源重建与剖视功能整体可靠：未发现 P0/P1，也没有发现此前 0.2.0 视觉问题（低高度横屏、材质释放）的回归。当前最需要处理的是两个构图/取景 P2：

1. 1280×900 桌面在面板默认展开时，默认视角与四个轴向预设均被面板覆盖，四角载荷标签也只能看到 2/4；应从布局上给相机留出安全区，或自动收起面板。
2. 390×844 竖屏默认取景仍裁切右前角，按 1 的三分之四视角严重溢出，与 README 的完整取景声明不符；应给透视预设增加基于车辆包围盒的窄屏 fit。

此外，遥测“六自由度积分与求解”行的名称在 1280 宽度下被压成单字竖排，属于可复现的排版失败，建议与 task-3 一并修复。P3（移动端底栏溢出、导出图 v0.2 版本标识）可在本轮一并清理，风险低。

若维持当前 README 的“移动端完整取景”表述，建议把上述两个 P2 作为本轮交付的修复条件；若本轮只做记录，则应同步修正 README 与 acceptance 的视觉声明，并在阶段三前补上取景/面板遮挡/导出内容的自动断言。
