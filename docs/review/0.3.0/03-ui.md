## 3. 发现详情（P1/P2）

### P1-1 三维相机的自由操作没有键盘路径（WCAG 2.1.1）

- **位置**：[`src/js/10-scene.js:1465-1484`](../../../src/js/10-scene.js#L1465-L1484)（pointerdown/move/up、wheel、dblclick）；[`src/js/30-ui.js:1245-1323`](../../../src/js/30-ui.js#L1245-L1323)（全局快捷键表无方向键、±、PageUp/Down）。
- **复现**：`node .tmp-review/ui/exp10-camera.mjs`。先用 `#btnHelp` 聚焦再 Shift+Tab 到 canvas，注入 ArrowLeft/ArrowUp/+/−/PageUp；随后在 canvas 上滚动滚轮。
- **期望 vs 实际**：期望文档承诺的“拖动旋转 / 滚轮缩放 / 右键平移”（`README.md:73-76`）有键盘等价操作或明确的替代控件。实际：按键后 `camera.theta=0.62`、`phi=1.22`、`zoom=5.79` 完全不变；滚轮后 `zoom 5.79 → 4.2657`（功能存在但仅指针可达）。按键在 canvas 上未触发任何视图变化（`exp10.log`）。
- **影响**：纯键盘/开关设备用户只能使用 5 个预设视角与重置，无法自由缩放观察悬架、摇臂、弹簧等阶段二演示内容。属于 WCAG 2.1.1 Level A 的功能不可达，且项目自述“键盘焦点/快捷键”在 UI 测试中被算作可访问性覆盖。
- **修复方向**：为 canvas 增加方向键旋转、Shift+方向键平移、`+/-/PageUp/PageDown` 缩放（或提供可见的缩放/平移控件）；在帮助模态的“操作与约定”中同步说明；回归测试用真实按键校验 `camera.theta/zoom` 变化。
- **置信度**：高（代码入口与运行时行为双重证据）。

### P2-1 Canvas 是首个 Tab 焦点但无可见焦点指示（WCAG 2.4.7）

- **位置**：[`src/js/10-scene.js:1590-1591`](../../../src/js/10-scene.js#L1590-L1591) 给 canvas 设置 `aria-label` 与 `tabindex="0"`；[`src/styles.css:1127-1129`](../../../src/styles.css#L1127-L1129) 的 `:focus-visible` 列表只覆盖 button/summary/chip/tool-btn/btn/text-btn/icon-btn，未覆盖 canvas，也没有全局 `canvas:focus-visible`。
- **复现**：`node .tmp-review/ui/exp8-focus-mobile.mjs`；聚焦 `#btnHelp` 后 Shift+Tab。
- **期望 vs 实际**：期望 `:focus-visible` 为 true 时存在可见焦点环。实际：`document.activeElement` 为 CANVAS，`matches(':focus-visible')===true`，但 `outline:none`、`boxShadow:none`；`focus-canvas.png` 上无任何视觉标记。AX 树确认 canvas 为 `role=Canvas`、name“方程式赛车三维动态底盘台”、focusable=true（`exp10.log`）。
- **影响**：键盘用户按一次 Tab 后焦点落在不可见的整屏元素上；此时 Space 又会切换仿真（canvas 不属于 `SHORTCUT_BLOCK_SELECTOR`），用户看不到焦点却触发状态变化。
- **修复方向**：增加 `#viewport canvas:focus-visible { outline: 2px solid ...; outline-offset: -4px; }`；并考虑把 canvas 从 Tab 序列移出（若无需键盘交互），或把它作为可操作区域并补齐键盘行为（与 P1-1 一并解决）。
- **置信度**：高。

### P2-2 选中态只用颜色表达，未暴露给辅助技术（WCAG 4.1.2 / 1.4.1）

- **位置**：模板 [`index.template.html:78-82`](../../../src/index.template.html#L78-L82)（路面预设）、[`:316-318`](../../../src/index.template.html#L316-L318)（N/kg）、[`:427-431`](../../../src/index.template.html#L427-L431)（相机预设）均无 `aria-pressed`/`role=radio`；对应同步函数只改 `.is-active`：[`30-ui.js:154-164`](../../../src/js/30-ui.js#L154-L164)（`updateRoadChips`）、[`:178-185`](../../../src/js/30-ui.js#L178-L185)（`applyUnit`）、[`:1065-1069`](../../../src/js/30-ui.js#L1065-L1069)（`syncCameraButtonActive`）。对照组：xray/ortho/autoRotate 都设置了 `aria-pressed`（[`:136-140`](../../../src/js/30-ui.js#L136-L140)、[`:201-204`](../../../src/js/30-ui.js#L201-L204)、[`:219-222`](../../../src/js/30-ui.js#L219-L222)、[`:1074-1076`](../../../src/js/30-ui.js#L1074-L1076)）。
- **复现**：`node .tmp-review/ui/exp1-baseline.mjs`、`exp6-state.mjs`、`exp8-focus-mobile.mjs`。检查 `[data-camera]/[data-units]/[data-road-preset]` 的 active 与 `aria-pressed`，以及 `Accessibility.getFullAXTree`。
- **期望 vs 实际**：期望屏幕阅读器能获知“当前单位=N、当前视角=三分之四、当前路面预设=水平”。实际：全部 `ariaPressed=null`、无 `role`；AX 中这些按钮只有 name、没有任何 pressed/checked/selected 属性；键盘用 Space 切换 kg 后，DOM 与视觉都变为 kg，但 AT 仍读不出选中项（`exp8.log` 的 `unitAfter`）。
- **影响**：单位切换会改变所有遥测数值的含义，但 AT 用户无法确认当前单位；相机/路面预设同样。选中态仅靠背景色/边框色，色觉障碍用户在弱对比下也难以辨认。这是“状态未暴露”而不仅是视觉偏好。
- **修复方向**：对单选组使用 `role="radiogroup"` + `role="radio" aria-checked`（或统一用 `aria-pressed` 并在组容器上加 `aria-label`）；同步函数同步属性；测试直接断言切换后的 `aria-pressed/aria-checked`。
- **置信度**：高。

### P2-3 功能性小标签对比度不足（WCAG 1.4.3）

- **位置**：[`src/styles.css:12`](../../../src/styles.css#L12) `--faint: #596678`；使用点（均为 `var(--faint)`）：[`:265`](../../../src/styles.css#L265) `.topbar-stat` 9.5px、[`:380`](../../../src/styles.css#L380) `.panel-kicker` 8px、[`:465`](../../../src/styles.css#L465) `.section-hint` 7.5px、[`:487`](../../../src/styles.css#L487) `.label-note` 9px、[`:539`](../../../src/styles.css#L539) `.range-scale` 7.5px、[`:738`](../../../src/styles.css#L738) `.total-strip span` 8px、[`:774`](../../../src/styles.css#L774) `.motion-strip span` 8px、[`:823`](../../../src/styles.css#L823) `.data-list dt` 8.5px；视口提示 [`:873-885`](../../../src/styles.css#L873-L885) 用 `rgba(156,170,188,0.45)` 8px。
- **复现**：`node .tmp-review/ui/exp1-baseline.mjs` 读取 computed color/font-size；`convert .tmp-review/ui/shot-1280x900.png -format '%[pixel:p{330,700}]' info:` 采样面板实际底色为 `srgb(12,16,23)`。
- **期望 vs 实际**：这些位置承载“车头抬高为正/右侧降低为正/含驾驶员/仅机构展示”“仿真状态/车体角速度/角点求解残差”“升沉/俯仰/侧倾/横摆”“平面倾角/动态总法向”等功能标签，属于需阅读信息，AA 要求 4.5:1。实际按 WCAG 公式：`#596678` 对 `rgb(12,16,23)` = **3.26:1**；视口提示混合色 `rgb(77,85,97)` = **2.53:1**；同时字号仅 7.5–9.5px。灰色 `--muted #8290a3` 为 5.87:1（合格），说明问题集中在 `--faint`。
- **影响**：低视力、强环境光或低质量投影下，滑块的语义注释与详细遥测行标签难以辨认；这不是纯装饰。
- **修复方向**：把功能性标签从 `--faint` 拆到新 token（例如 `#7c8a9d`，对实测底色为 5.43:1），仅把 `panel-kicker/section-hint` 等装饰性英文小标题保留 `--faint`；同时把 7.5–8px 提高到 ≥10px。回归可用计算色/像素采样对比度断言。
- **置信度**：高（颜色为常量、底色实测；仅“是否属于纯装饰”存在解释空间，我按功能标签计入）。

### P2-4 桌面默认视口下视口提示与底栏重叠

- **位置**：[`src/styles.css:835-853`](../../../src/styles.css#L835-L853) `.bottom-bar`（z-index:40，bottom:20px，居中）；[`:873-888`](../../../src/styles.css#L873-L888) `.viewport-hint`（z-index:40，right:26px，bottom:28px，`pointer-events:none`）；模板 [`index.template.html:425-449`](../../../src/index.template.html#L425-L449) 中 hint 在 bar 之后，同 z-index 下绘制在上层。
- **复现**：`node .tmp-review/ui/exp4-overlap.mjs`。1280×900 实测：bar `l=324.9,r=955.1,t=835,b=880`；hint `l=840.6,r=1254,t=860,b=872` → 水平重叠 114.5px、垂直重叠 12px。1280×720、1366×768、1440×900 同样重叠；1600×900 不重叠。放大截图 [`crop-overlap-zoom.png`](../../../.tmp-review/ui/crop-overlap-zoom.png) 可见“拖动旋转 · 滚轮缩放至光标”画在“重置视角/截图”按钮区域上。
- **期望 vs 实际**：期望提示与工具栏互不遮挡。实际：默认桌面宽度 1280–1440 下，提示文字覆盖底栏右端两个按钮的下缘；因为 `pointer-events:none`，按钮仍可点击，属视觉/可读性缺陷而非功能阻断。
- **影响**：1280/1366/1440 等常见笔记本分辨率下，主操作“截图/重置视角”的文字被无关提示叠压，降低可读性；也说明“无页面溢出”类测试不足以发现层内重叠。
- **修复方向**：把 hint 放到 bar 上方（例如 bottom: 76px）或把断点从 1180 提高到 ~1560；或让 hint 在 `max-width:1500px` 隐藏。回归断言两矩形不相交，而不只是各自在视口内。
- **置信度**：高（几何测量 + 截图）。

### P2-5 测试有效性缺口：45 项全绿仍可放过上述缺陷

### 5.1 现有 UI 测试的断言边界

1. **视口覆盖**：[`test-ui-browser.mjs:167`](../../../tools/test-ui-browser.mjs#L167) 四组视口没有 390 或 320 宽。README 宣称“竖屏手机”抽屉（`README.md:83`）与 390×844 截图（`docs/05-mobile.png`），但自动化从未在 390 宽下断言。结果是 P3-1 的底栏裁切与 P2-4 在 1280 宽的重叠都落在测试外。
2. **只测自身矩形**：[`:173-175`](../../../tools/test-ui-browser.mjs#L173-L175) 的 `inView` 只用于 topbar/bottom-bar 自身；底栏子按钮可被内部 `overflow-x:auto` 裁掉而 topbar/bar 的 rect 仍然“在视口内”。[`:183-184`](../../../tools/test-ui-browser.mjs#L183-L184) 的“panel stays inside the viewport”只查 `top/bottom/open`，**完全不检查 left/right**，因此面板若整体横向滑出仍会通过；`screenshot` 按钮也只查 top/bottom。
3. **键盘只查位置，不查可见性**：[`:245-291`](../../../tools/test-ui-browser.mjs#L245-L291) 验证了 inert、焦点回返、Tab 不进入关闭面板与模态陷阱，这些都是有效行为断言；但没有一处检查 `:focus-visible` 的计算 outline/box-shadow。P2-1 因此不可见。
4. **状态只查开关，不查选择**：[`:219-223`](../../../tools/test-ui-browser.mjs#L219-L223) 只验证参数/遥测按钮的 `aria-expanded`；没有任何测试检查 `[data-units]/[data-camera]/[data-road-preset]` 的选中态是否暴露给 AT。P2-2 因此不可见。
5. **对比度/缩放/触控/减少动态无断言**：没有 computed color 采样、没有 200% 缩放（683×384 或 320 宽）后的布局断言、没有触控尺寸、没有 `prefers-reduced-motion`。P2-3/P3-10/P3-12/P3-7 都不在套件内。

7. **弱断言**：[`:362-364`](../../../tools/test-ui-browser.mjs#L362-L364) 自检只数 `li` 数量；[`:386`](../../../tools/test-ui-browser.mjs#L386) B5.4 只要求 `>=3` 与 `>0`（文档引用 7/387）；[`:295-299`](../../../tools/test-ui-browser.mjs#L295-L299) 忽略前置 `openPanelStable` 返回值。这些不影响当前通过，但降低了回归灵敏度。
8. **测试目标与产物**：[`:158-159`](../../../tools/test-ui-browser.mjs#L158-L159) 从 `src` 重新构建到临时目录再测，不直接测仓库 `index.html`；`build:check` 另行保证一致。流程上可接受（acceptance §5 也要求先 build:check），但“UI 测试通过”不等于“已提交产物通过”，值得在文档中写清。

## 6. 关于“设计已声明的简化”与实现缺陷的区分

- **动态自检在参数变化后仍显示上一次结果**：这是 README 明确声明的行为（“参数变化后遥测中的‘动态自检’显示最近一次结果”，`README.md:188`）。本轮实测 mass 760 后 `selfTestRuns.static` 3→4、dynamic 仍 1，遥测行仍“10 / 10 通过”（`exp7.log`）。这不是缺陷，但建议加“上次结果”角标，避免用户误读为当前参数已验证。
- **暂停后“重置姿态/回到平衡”恢复运行**：现有测试 `reset from pause returns to running` 明确固化了这一行为；README 的暂停文案未提及。属于文档与实现的口径差，不列入缺陷，建议在 README 的按钮表中补一句。
- **DPI 与固定阈值**：测试 runner 强制 `--force-device-scale-factor=1` 且 `deviceScaleFactor:1`，所以现有阈值不会因宿主 DPI 假失败；但套件内仍有大量固定 sleep（`sleep(80/180/200/250/300/320/420/500/700)`）。本轮在 SwiftShader 0.3–2 fps 的极端负载下官方套件仍 45/45 通过（§8），说明现有轮询/超时余量足够；B6 把最易抖的路径换成 rAF 轮询方向正确。剩余风险主要是未来加入更短动画或更紧超时后，固定 sleep 会再次成为不稳定源；建议改为“状态/动画结束”轮询（例如等待 `panel.getAnimations().length===0` 或 computed transform 为目标值）。
- **固定阈值在别的字体下**：页面全部用 px，系统字体放大不会重排（见 §7）；浏览器缩放会按 CSS 像素重排，已用 683×384/320×568 模拟，未发现页面级溢出。测试的 `netHeight >= 55%`、面板 top/bottom ±1 等阈值与字体无关，风险主要在固定 sleep，而非数值容差。

## 7. 覆盖限制

1. **宿主负载与软件渲染**：审阅期间 `uptime` load average ≈31（12 核）；无头 Chrome 使用 SwiftShader，实测 `requestAnimationFrame` 约 0.3–2 fps（`diag5-fps.mjs`、`diag6-raf.mjs`）。因此 CSS transition 可在数百毫秒内停在 0% 进度，媒体查询 change 回调也可能延迟。本文所有“布局/DOM/键盘/AX”结论来自同步路径，不受帧率影响；涉及动画时序的观察（§4.1）已标注环境放大因素，不作为确定的用户体验缺陷。
2. **未使用真实屏幕阅读器**：只有 Chrome Accessibility 树，没有 NVDA/JAWS/VoiceOver 实读。AX 属性（pressed/checked/live）与可访问名是可靠的，但朗读顺序与重复播报未验证。
3. **未在真实移动设备/iOS 验证**：390×844/320×568 是 CDP 视口模拟，`env(safe-area-inset-*)` 与动态地址栏不可模拟；P3-11 明确标为待真机验证。
4. **200% 缩放用视口折半模拟**（683×384），不是真实 Chrome page zoom；对布局重排等价，但对文字物理尺寸/亚像素渲染略有差异。系统字体放大（Chrome 默认字号/最小字号）未测；页面使用 px，本身不会随系统字号变化，这是页面层面的可访问性限制（非本轮实测缺陷）。
5. **未验证截图下载落盘**：`exportScreenshot()` 触发的 `a.click()` 在无头环境可能被下载策略拦截；仅在代码层确认 toast/导出路径。复制参数主路径与失败回退分别实测。
6. **未做长时间监听器/内存泄漏测量**：代码路径显示 `bindControls`/`bindKeyboard`/`bindWindowChrome` 都只在 `initUI()` 一次执行，面板/重建走事件委托或复用节点，未发现重复绑定；但未做堆快照对比。
7. **官方套件复跑结果**：本轮独立复跑为 45/45 PASS（§8），与 Lead 基线一致；但本报告的主要结论仍以逐项 CDP 探针为准，因为套件本身对 P1/P2 缺陷没有断言（§5）。
8. **探针未覆盖**：3D 视口内的遮挡/可读性、GPU 上的真实阴影/动画质量、打印样式、高对比度模式（forced-colors）、屏幕旋转过程中的连续帧表现。

该轮运行发生在宿主 load average ≈31、SwiftShader 0.3–2 fps 的同一环境，45 个 `ok`、0 个 `FAIL`，Chrome 进程由 finally 清理。两点说明：

1. 它证明 B6 的稳定性修复（rAF 轮询、openPanelStable、等待 matchMedia）在当前极端环境下仍可全绿，Lead 的基线可信。
2. 同一份日志中 `1280x720 layout fits the viewport` 的 bottomBar 矩形就是 `left=324.87, right=955.13`，与 P2-4 的重叠测量完全一致；该断言只比较 bar 自身与视口，因此套件通过并不否定 P2-4/P2-5。

## 9. 结论

0.3.0 的 U1–U4 修复经真实浏览器行为验证成立：横屏布局、空格与控件的竞争、面板 inert/焦点回返、暂停四字段同步都没有回归；模态框焦点陷阱、存储恢复、主路径复制、自检列表读屏可读性也正常。未发现 P0 或影响物理/构建的 UI 问题。

主要残留风险集中在三类：

1. **键盘可达性**：三维相机没有键盘路径（P1-1），画布作为首个焦点站没有可见焦点（P2-1）。这两项合起来意味着“只用键盘的用户无法完整使用这个 3D 演示，而且不知道焦点在哪”。
2. **状态语义与可读性**：单位/视角/路面预设的选中态未暴露给 AT 且仅靠颜色（P2-2）；功能标签对比度 3.26:1、字号 7.5–9.5px（P2-3）；默认桌面分辨率下提示文字压住底栏按钮（P2-4）。
3. **测试有效性**：45 项套件的断言边界停在“元素存在/状态类名/焦点归属”，没有覆盖竖屏窄宽、子元素溢出、层间重叠、选中态语义、焦点可见性、对比度、缩放与触控；因此上述 P2 都能在 CI 全绿时存在（P2-5）。

优先修复顺序建议：P1-1 + P2-1（同一处键盘/焦点改造）→ P2-2 → P2-3 → P2-4 → P3-2/P3-3（暂停语义）→ 其余 P3 与测试补强。
